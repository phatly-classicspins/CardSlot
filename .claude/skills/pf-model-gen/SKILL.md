# model-gen — 3D models the design package does not supply

An approved design package or an artist's FBX comes first. A model that exists there is used as-is,
and is never regenerated. This skill is for the models nobody supplied. A 2D sprite, emblem or
backdrop is `pf-asset-gen`, not this.

## Two stages, one checkpoint between them

| Stage | Who draws | What the tool measures | Who decides |
|---|---|---|---|
| **Blueprint** | Codex image_gen: one 2×2 orthographic sheet per variant | all four views present, none crossing the grid, each view's proportions against the requested size (±15%) | a person picks a variant and approves it |
| **Model** | Codex writes a `bpy` script (read-only, no workspace); the tool runs it in Blender | bounding box ±3%, ground/centre pivot, triangle budget, palette materials, required parts; outline match per view against the blueprint | a person picks by looking at `hero.png` and `compare.png` |

The checkpoint is the blueprint. It costs about a minute to redraw; a model round costs minutes. In an
interactive run, never `build` from a blueprint the user has not approved. Approval means `status:
approved` in `blueprint.png.gen.json`, written when they say so. `build` warns on anything else.

## The tool and the data

The tools are `Tools/pf/model-gen.py` and its Blender half `Tools/pf/model-gen-blender.py` (both
synced from the framework). The blueprint call goes through `Tools/pf/asset-gen.py`. The data is the
SKU's own, under `Tools/ModelGen/` (`MODELGEN_ROOT`):

| Path | What | Committed |
|---|---|---|
| `Tools/ModelGen/requests/<id>.json` | the request: reviewable | yes |
| `<out>/` (the request's `out`) | `blueprint.png`, `build.py` (the source), `<id>.fbx`, `views.png`, `hero.png`, `compare.png`, plus `blueprint.png.gen.json` and `model.gen.json` | yes |
| `Tools/ModelGen/candidates/<id>/` | every variant, every round, every log | no. The tool writes its own `.gitignore` |

Keep `out` **outside `Assets/`**. Importing the FBX is the consuming story's job.

## The request

`schema: model-gen-request/v1`, repo-relative paths. The full field list is in `model-gen.py --help`.

| Field | Meaning |
|---|---|
| `id` | one path segment |
| `subject` | what it is, in a sentence or two, with the look. Both stages read it |
| `size` | `{width, height, length}` metres, the **overall** box (mirrors, bumpers, wheels included). Take it from the GDD's layout numbers when they exist. It wins over the blueprint |
| `palette` | `{key: "RRGGBB"}` from DESIGN.md colours. The only colours; materials arrive as `M_<key>` |
| `max_tris` | the budget after bevels, from the GDD's performance budget |
| `parts` | `[{name, note}]`: what moves (a wheel, brush, fan, door), so it stays a separate object with its origin at the pivot |
| `references` | approved art the look follows (style only) |
| `notes`, `hero`, `consumer` | guidance for both stages · the 3/4 render angle · who imports it |

## The flow

```sh
python3 Tools/pf/model-gen.py blueprint        Tools/ModelGen/requests/<id>.json --variants 2
python3 Tools/pf/model-gen.py select-blueprint Tools/ModelGen/requests/<id>.json <n>
#   the user approves -> status: approved in <out>/blueprint.png.gen.json
python3 Tools/pf/model-gen.py build            Tools/ModelGen/requests/<id>.json --rounds 3
python3 Tools/pf/model-gen.py select           Tools/ModelGen/requests/<id>.json <n>
python3 Tools/pf/model-gen.py status           [--under <dir>] [--md <dir>/MODELS.md]
```

**Run it unsandboxed.** It needs the network. A blueprint variant takes about a minute. A build round
is one Codex call (minutes) plus Blender (seconds), so **run `build` in the background**. A round
stops the chain early once every check passes at the target outline match. `--dry-run` prints the
prompt without spending anything.

Exit codes: `0` ok · `1` no variant passed, or a committed file no longer matches its provenance · `2` error.

## The FBX contract (what the import story relies on)

- Metres at import scale 1. The front faces Unity **+Z** and Y is up. The axis change is baked into
  the meshes, so the root arrives at identity (no -90° X); a part keeps only the rotation its script gave it.
- The pivot is bottom-centre: the lowest point is on y = 0 and the box is centred on x = 0, z = 0.
- It is triangulated exactly as Blender cut it, with one material per palette key named `M_<key>`.
  Remap those to the SKU's shader by name; never hand-assign them.
- Required parts are separate objects under their exact names, each with its origin at its pivot.

**The rig.** The framework rig is 1 px = 1 world unit. Where a metre-scale model sits in that world
(its camera, RenderLayer and scale) is an architecture decision, so route it. Never bake a rig scale
into a request.

## Choosing

- **Blueprint.** Look at every variant. The verdict screens out a crossed grid and wrong proportions.
  Then check what it cannot: the side view's front points **left**, the top view's front points
  **down** (otherwise the model comes out mirrored), and no text or labels. Choose the design, not
  the numbers.
- **Model.** Open `hero.png` and `compare.png` for each variant's best round. The outline match ranks
  rounds; it does not approve one. At an equal look, take fewer triangles.
- **A small fix.** Edit `<out>/build.py` and run `rebuild`. It is cheaper than another round, and the
  provenance records the edit.

## Budget and stopping

- Blueprint: at most 2 rounds of 2 variants. If both rounds miss, the `subject` or `notes` is the
  problem.
- Model: by default 1 variant × 3 rounds, and at most about 6 Codex calls per model. If two builds
  miss, fix the request, not the luck. Typical causes: a size that contradicts the blueprint, a budget
  too tight for the part count, or a vague subject.

## What a generation is not

- **Not deterministic.** Neither stage repeats, so the selected files are committed **source**, and
  nothing regenerates them in CI. The script itself is deterministic (randomness is refused), so
  `rebuild` gives the same geometry. Only the FBX bytes differ, by the exporter's timestamp.
- **Not finished.** Both selections are `status: pending-user-review` until a person approves them.
- **Not an import.** Nothing is written under `Assets/`.

## The script is model-written code

Before Blender runs it, the tool screens it. It may import only `bpy`, `bmesh`, `math` and
`mathutils`, and it may not use `bpy.ops`, `bpy.app`, `bpy.utils`, `bpy.data.materials` or `texts`,
`open`, `exec`, `getattr` or dunder attributes. Blender runs `--factory-startup` from a temporary
directory, under a timeout. That is a screen, not a sandbox: read `build.py` before you commit it.

## In a bmad-ux run

The framework's BMAD layer (`_bmad/custom/bmad-ux.pf.toml`) makes bmad-ux decide at Discovery whether
the game's world is 3D and, if so, agree a model list with the user. At Finalize it runs this flow per
model, with `out: {doc_workspace}/models/<id>` and the approved mockups as references, and writes
`MODELS.md` with `status --under {doc_workspace} --md {doc_workspace}/MODELS.md`. `bmad-architecture`
reads that `MODELS.md` as an input. Then `pf-ux-asset-handoff` inventories every model (these and any
supplied FBX/glTF) and every animation clip into `models/model-manifest.json`, and maps each one's
import scale, host and clips in ASSET-MAP.md. This tool bakes no animation (`bake_anim=False`): rigs
and clips come from whoever owns animation, and the handoff checks them.

## Why the wrapper

- **The model only writes text.** Given write access, a model post-processes its own output without
  saying so. So Codex runs `-s read-only` from a temporary directory outside the repo; the reply
  carries the script, and the tool runs, measures, exports and renders.
- **The comparison closes the loop.** Codex never sees Blender. Each round it gets the blueprint, its
  previous script, the failed checks and a picture of its render beside the blueprint, view by view.
