# Story preflight

Procedure detail: the eight checks in `docs/framework/recipes/story-preflight-checks.md`, the
per-auditor prompt in `docs/framework/recipes/story-preflight-auditor-brief.md`, the known-answer case
in `docs/framework/recipes/story-preflight-calibration.md`. Mechanical step:
`Tools/pf/preflight-index.py` (`--help`).

## Why this exists

Measured on a SKU: a story passed a document review and still stopped the loop at planning. AC 4 said
an 8-node chain hangs vertical after 240 steps; with the frozen `chain-motion.md` parameters it is still
3.55 card heights off at step 240 and first gets within 0.01 at step 1,701. AC 5's "random pin walk"
never said how far the pin moves per step, and that number alone decides pass or fail. Neither problem
is visible by reading — both appear the moment someone measures, or starts writing the test.

The dev session is built to stop there. The loop hands it an **intent contract** — in sprint mode the
story's whole block in `epics.md` (a SKU's `_bmad/custom/bmad-build-auto.toml` usually pins this as the
story source of truth), in stories mode `SPEC.md` + its companions + the story's `stories.yaml` entry —
and `bmad-build-auto` HALTs `blocked` on an `intent gap` whenever a bound cannot hold or two defensible
readings lead to different outcomes. It is told never to reword or retune its way out. So each such gap
costs a paused run and a human round-trip mid-sprint. Where the text has two readings and the session
does not notice, it is worse: it picks one, its own tests pass, and nobody notices.

This skill does the measuring and the test-writing-in-your-head up front, for many stories at once, and
brings the human one batch of decisions instead of one interruption per story.

## Ground rules

- **The audit is read-only.** You write only the report (under `{planning_artifacts}/preflight/`),
  throwaway scripts in the scratchpad, and — after the human decides — the amended intent text.
- **Never touch** `sprint-status.yaml`, a story spec's `status:` field, `stories.yaml`, `.memlog.md`,
  `.bmad-loop/`, code or tests. Never run Unity, batchmode (`pf-build.sh test|content|player`) or play
  mode: this is a documents-plus-Python job.
- **SPEC.md has one writer.** It is derived from `.memlog.md` by `bmad-spec`; a hand edit is overwritten
  on the next derive. In stories or spec mode an amendment goes to `bmad-spec`, never into SPEC.md.
- **The human decides every amendment**, including the obvious ones. An obvious fix picked by the auditor
  is exactly the silent guess this skill exists to prevent. Recommend; don't decide.
- **A done story is history.** Report a problem in one as a follow-up for `bmad-correct-course`; do not
  edit its block or its story spec.
- **Stay out of the loop's way.** When the SKU has `.bmad-loop/`, run `bmad-loop status` first. Never
  amend the story the loop is currently driving. Amend while no run is live, or only stories well ahead
  of the current one, and remind the human to commit the amendments before the loop reaches them (the
  loop commits on the branch it runs on).

## Workflow

### 1. Scope

Default: every story not `done` (stories mode: every story without a `done` story spec; spec mode: every
CAP). If the user gave no scope and the backlog is large, offer "the next epic the loop will reach"
first (stories mode: the next few stories in `stories.yaml` order). When budget is tight, go in this
order: function stories with a numeric Self-check unknown or quantitative ACs → logic stories
(exactly-once, idempotency, ordering, clocks) → UI function stories → finish stories (inputs only —
checks B7, B8). In stories or spec mode, rank by the CAP's `success:` line the same way.

### 2. Index

```bash
python3 Tools/pf/preflight-index.py --scope remaining --out <scratchpad>/index.md
python3 Tools/pf/preflight-index.py --scope epic:2 --format json --out <scratchpad>/index-e2.json
```

The tool finds the intent source itself: `.bmad-loop/policy.toml` `[stories] source = "stories"` →
stories mode on its `spec_folder`; else `{planning_artifacts}/epics.md` → epics mode; else the one
`_bmad-output/specs/*/SPEC.md` → stories mode when a `stories.yaml` sits beside it, spec mode when not.
Force a source with `--source`, `--epics` or `--spec-folder`. Exit `2` names what it could not find.

Scopes: `remaining` · `all` · `epic:2,5` · `story:2.4,9.1` (epics) · `story:1,3` (stories) · `cap:1,4`
(stories: the stories naming those CAPs; spec: those CAPs).

The **Project map** at the top is where this SKU keeps what its stories cite — the SKU code root, the
engine-free test roots, the framework API index, the architecture spine, the UX packages, the spec
folders, prior preflight reports, this SKU's calibration cases, both languages, and the git sha of the
intent. In epics mode it adds the shared sections (conventions, the decision table, the human checklist)
with line ranges and every epic's shared-rules range; in stories or spec mode, the companions (a missing
one is flagged), the open questions, the assumptions and any CAP no story names.

Per story it lists — epics mode: kind, sprint status, an existing spec and its status, depends-on (with
status, and a warning for a dependency the loop reaches later or an id not in epics.md), freezes,
context to load, decision rows cited, the Self-check unknown, heuristic flags per AC and for the Render
Floor / Visual Contract text (`numeric`, `random`, `vague`, `block_if`), referenced paths missing today
and whether anything produces them, and the other stories that touch this story's frozen contract.
Stories mode: the story spec and its status, description, `invoke_dev_with`, the CAPs it names (with
SPEC.md lines; ⚠ for an unknown CAP or none), flags per CAP success line and on the description, missing
paths, and the other stories naming the same CAP. **Flags say where to read, not what is wrong** — most
flagged ACs are fine, and an unflagged one can still be ambiguous.

### 3. Audit

Per story, read:

- **epics mode** — its whole block (line range from the index); the shared sections the index lists
  (the conventions and Definition of Done, each decision row it cites, the human checklist when B6 is in
  play); its epic's shared rules; the sections its *Context to load* names, resolved through the Project
  map; the related stories the index lists; and, for dependencies already done, the real code of the
  contract it consumes (the SKU root and test roots; PF types through
  `docs/framework/framework-api.index.json`).
- **stories or spec mode** — its `stories.yaml` entry; every CAP it names, intent and success; SPEC.md's
  Constraints, Non-goals, Assumptions and Open Questions; the companion sections each CAP cites (a CAP
  that says `GDD/03 §3.4` means that companion's section); the other stories naming the same CAP; and,
  for stories already done, the real code.

Then apply the eight checks in `docs/framework/recipes/story-preflight-checks.md` to the whole block —
the implementation notes' names, formulas and method contracts are intent too. The core move for
every AC or success line: **write its test in your head.** If you cannot write it without choosing a
number, a fixture or a reading the text does not give you, that is a finding. If you can, ask whether it
passes with the frozen inputs — and if the answer depends on behaviour, measure it (step 4).

**Fan out** when the scope is more than about four stories: one `general-purpose` Agent per epic (stories
mode: per run of about six consecutive stories), all launched in one message, each given
`docs/framework/recipes/story-preflight-auditor-brief.md` with its story list and index rows filled in.
Use the Workflow tool only if the user explicitly asks for a workflow. Auditors return findings in the
schema below; you consolidate, dedupe (a cross-story contradiction is one finding with two sides), and
re-check anything marked BLOCKER before it reaches the human.

### 4. Measure

For B1 claims, and to sweep a B2 free value, reproduce instead of arguing. Write a throwaway Python
script in the scratchpad from the cited listing, the frozen parameter values and the fixture the AC
describes — verbatim, no "improvements" — run it, and keep the numbers and the script path. For an
undefined input, sweep it and report where pass flips to fail; that turns the human's question into a
choice between numbers. Say so if float64 vs the C# float32 could plausibly matter: it rarely does at the
gaps that make findings, but it decides exact counts and boundary equalities — emulate float32 there
(B1 in the checks recipe).

When a claim depends on code that does not exist yet and the docs do not pin enough to simulate it,
record it under **Unmeasurable now** with what would settle it and which story will — it is not a
finding, and inventing a model to force a number is the same guess this skill exists to prevent.

**Calibration.** Before a broad audit (or whenever you doubt the depth), run your process on the
known-answer case in `docs/framework/recipes/story-preflight-calibration.md` — the story above, with
its frozen parameters, self-contained. It must produce AC 4 → B1 BLOCKER, AC 5 → B2 BLOCKER and
`FitsLongestChain` → B3 RISK with the numbers that recipe gives. When the index names a SKU calibration
file (`{planning_artifacts}/preflight/calibration.md`), run its cases too. A process that misses them is
too shallow for the rest.

When a story this preflight passed still blocks the loop, add it to that SKU file — the git sha and line
range of the text as it was, and the findings it must produce (format in the calibration recipe). That
is how the next preflight in this SKU gets deeper.

### 5. Report

Write `{planning_artifacts}/preflight/preflight-<YYYY-MM-DD>-<scope>.md` from the template below. Write
it in the `document_output_language` the index prints (English by default), because its text gets
quoted into the intent contract; talk to the human in their `communication_language`.

### 6. Decide

Present BLOCKERs first, then RISKs, grouped by story in loop order. Use AskUserQuestion, at most four
questions per call, recommended option first with "(Recommended)", and put each option's measured
consequence in its description. List NOTEs without asking. Record every answer in the report's
Decisions table as you go, so a long session survives a context reset.

### 7. Amend

For each decision:

- **epics.md (epics mode):** edit the story block minimally, so exactly one reading remains and every
  number the test needs is stated; keep the Given/When/Then shape. Then add one line to the story block
  just before `**Self-check:**` (or at its end when it has none) —
  `**Preflight <date>:** AC <n> — <what changed and why, with the measured number>.` — so the dev
  session sees why the AC reads the way it does.
- **SPEC.md (stories or spec mode, or a number SPEC.md also states):** hand the decided changes to
  `bmad-spec` (update the spec) as one batch — per decision the CAP or section, the new wording or
  number, the measured evidence and the finding id. `bmad-spec` appends each to `.memlog.md` and
  re-derives SPEC.md; a change that overrides a companion (a GDD table, a parameter doc) names that file,
  and `bmad-spec` offers to update the source. A `stories.yaml` description that points at the wrong CAP
  or bundles two unknowns goes the same way, to its Story Breakdown.
- **Existing story spec:** if the index shows one (`spec-X-Y-*.md`, or `<spec folder>/stories/<id>-*.md`)
  and the story is not done, mirror the change in the spec's AC and add a `## Spec Change Log` entry.
  Leave its `status:` alone.
- **Cross-story:** a contradiction between two stories is amended on both sides in the same pass.
- Show the human a summary of the changes. Do not commit unless they ask; remind them to commit before
  the loop reaches the amended stories.

## Severity

- **BLOCKER** — the dev session's planning will stop: a bound that measures false with the frozen
  inputs, a pass/fail that depends on an unstated value, an AC that requires something the rules forbid,
  a needed contract that no story freezes.
- **RISK** — the session can proceed only by picking a reading or a value, and a wrong pick passes its
  own tests. Treat it as seriously as a BLOCKER; it just fails later and quieter.
- **NOTE** — drift that changes nothing testable: a typo, a stale reference with an obvious target, a
  tautological assertion that still passes.

## Finding schema

Auditors return exactly this, and the report is built from it:

```yaml
findings:
  - id: "2.4-AC2-B1"          # <story>-<where>-<check>; stories mode "<id>-CAP3-B1"; spec mode "CAP3-success-B1"
    story: "2.4"              # story id, or the CAP id in spec mode
    where: "AC 2"             # AC n | CAP-n success | description | notes | Depends on | Render Floor | Visual Contract | Out of scope | Constraints
    file: "_bmad-output/planning-artifacts/epics.md"
    line: 812                 # line of the quote in that file
    check: B1                 # B1..B8, see docs/framework/recipes/story-preflight-checks.md
    severity: BLOCKER         # BLOCKER | RISK | NOTE
    quote: "<verbatim text, at most two lines>"
    problem: "<one sentence>"
    evidence: "<measured numbers + script path, or file:line of the other side>"
    options:
      - "(recommended) <option> — <consequence>"
      - "<option> — <consequence>"
unmeasurable_now:
  - { story: "2.5", where: "AC 3", needs: "<what would settle it>", settled_by: "2.4" }
checked_clean: ["2.1", "2.2"]  # stories audited with no finding
```
