# BMad — Archive Completed Epics & Stories

Move **finished** BMad planning/implementation artifacts out of the active
`_bmad-output/` working set into a dated, git-history-preserving archive, so the
next `bmad-spec` → `bmad-create-epics-and-stories` → `bmad-sprint-planning` cycle
starts on a clean slate — **without losing open work**.

This is a housekeeping skill; BMad itself has no archive step. It never deletes;
it only **moves** (via `git mv`) and **extracts** open items forward.

## Inputs (args)

- `mode` — `fresh` (default) or `continue`.
  - **`fresh`** — the next spec is disparate from what shipped; archive *everything
    done*, including `epics.md`, so a brand-new epics file can be authored.
  - **`continue`** — the next work continues the same epic line (Epic N+1); **keep
    `epics.md` in place** (new epics get appended) and archive only the done story
    files, retros, and the old `sprint-status.yaml`.
- `label` — short slug for the archive folder, e.g. `framework-m0-m6`. If omitted,
  derive one from the archived epic range (e.g. `epics-1-6`).

Ask the user for `mode`/`label` only if genuinely ambiguous; otherwise infer and
state the choice.

## Preconditions — verify before moving anything

1. **All target work is actually done.** Read
   `_bmad-output/implementation-artifacts/sprint-status.yaml`. Every story under the
   epics being archived must be `done` and each `epic-N-retrospective` `done`. If any
   story is not `done`, **stop and report which** — do not archive in-progress work.
   Flip any lingering `epic-N: in-progress` whose stories are all done to `done`
   first (report it).
2. **Repo is git-tracked** under `_bmad-output/` (it is). Use `git mv` so history
   follows the files. If a target file is untracked, fall back to plain `mv`.

## Procedure

Today's date comes from the session context — use `YYYY-MM-DD`.

### 1. Create the archive tree

```
_bmad-output/_archive/<YYYY-MM-DD>-<label>/
  planning/
  implementation/
```

### 2. Move completed artifacts (git mv)

**Always archive (both modes):**
- `implementation-artifacts/<E>-<S>-*.md` — every done story file
- `implementation-artifacts/epic-*-retro-*.md` — retrospectives
- `implementation-artifacts/sprint-status.yaml` — the finished sprint (a new one is
  regenerated by `bmad-sprint-planning` from the next `epics.md`)
- `implementation-artifacts/spec-*.md` — completed quick-dev / correction specs
- `implementation-artifacts/tests/` — per-story test & QA-e2e summaries
- `planning-artifacts/implementation-readiness-report-*.md` — readiness report(s)

**`fresh` mode also archives:**
- `planning-artifacts/epics.md`

**`continue` mode keeps** `epics.md` in place.

**Never archive (forward-looking / foundational — leave in place):**
- `planning-artifacts/architecture/`, `planning-artifacts/prds/` — foundation still
  reflected in the codebase
- `_bmad-output/specs/spec-prototype-framework/` (or the project's founding SPEC)
- `implementation-artifacts/deferred-work.md` — **open** framework debt; carries
  forward. (If the user explicitly wants a total reset, archive it too — but ask.)

### 3. Preserve open work — write `carry-forward.md`

Before the sprint-status file is archived, extract every `action_items` entry whose
`status` is **not `done`** and write them to a fresh
`_bmad-output/implementation-artifacts/carry-forward.md` with: a pointer to the
archive folder, the open action items grouped by epic (verbatim `action` + `owner`),
and a pointer to `deferred-work.md`. This is the memory a new sprint would otherwise
lose. If there are zero open items, note that instead.

### 4. Write an archive index

Create `_bmad-output/_archive/<YYYY-MM-DD>-<label>/README.md` listing: date, mode,
epic range archived, a one-line manifest of what moved, and the founding docs left
in place. This makes the archive self-describing.

### 5. Report

Summarize: files moved (counts by category), the archive path, the
`carry-forward.md` open-item count, what was intentionally kept, and the **next
step** — a fresh-context `bmad-spec` (then `create-epics-and-stories` →
`check-implementation-readiness` → `sprint-planning`). Do **not** auto-run the next
BMad skill.

## Guardrails

- **Move, never delete.** Everything is recoverable from the archive folder / git.
- **Don't touch code** (`Assets/`, `Packages/`, `Tools/`, `HeadlessTests/`) — this
  skill only reorganizes `_bmad-output/`.
- **Don't lose open items.** The `carry-forward.md` step is mandatory whenever the
  archived `sprint-status.yaml` has non-`done` action items.
- Prefer one batched `git mv` per category; report any path that fails to move
  rather than aborting the whole run.
